# 2026-04-13 — MemPalace setup + port stabilisation

## What we started with

- Fresh clone of `mempalace` on branch `feat/convert-to-rust`. Rust port phase
  7 "done", but the CLI was in fact still using `InMemoryPalace::new()` —
  `--palace <PATH>` was parsed and ignored. Mining "worked" but silently threw
  everything away on process exit.
- Two remotes (`origin`, `upstream`), history full of port commits, legacy
  Python still on disk under `legacy/` + `hooks/` + `.claude-plugin/` +
  `.codex-plugin/` + `benchmarks/` + `examples/`.
- Four AI agents configured on this box but none had mempalace wired in.

## What we did

1. **Security audit** — read-only sweep of the whole repo to prove it wasn't
   malware. Verdict: clean. No TLS bypass, no credential harvest, no listening
   sockets. Only outbound path is `fastembed` → HuggingFace for the embedding
   model on first run.
2. **History nuke** — removed remotes, wiped `legacy/ benchmarks/ examples/`,
   orphan-branch reset to a single `Initial commit`. Kept `hooks/` because you
   only said remove `legacy/`.
3. **Build + `init`** — `cargo build --release`, symlinked to
   `~/.local/bin/mempalace`, ran `mempalace init`.
4. **Wired 4 agents** over MCP — Claude Code, opencode, Codex, Gemini — all
   initially with `--palace ~/.mempalace`.
5. **Dry-run mining** of Claude Code convos + Codex + 43 tardis projects.
   Stats looked great: 348k drawers. Then `status` showed **0 drawers.**
   Discovered `main.rs:127` hardcoded `InMemoryPalace` and ignored `--palace`.
6. **Fix 1 — wire `--palace` to `LanceDbPalace`.** Added an `open_palace()`
   helper in `mempalace-cli/src/main.rs`, fixed `cmd_mcp_serve` to construct
   the palace before the tokio runtime (LanceDbPalace refuses to build inside
   a running runtime), made `KnowledgeGraph` honor the palace path too. Smoke
   test with 34 drawers: persistence confirmed, semantic search works.
7. **MCP configs updated** to pass `--palace ~/.mempalace`.
8. **Fix 2 — batched ingest.** Added `Palace::add_many` trait method with a
   default loop impl, then overrode it in `LanceDbPalace` to embed 64 rows per
   fastembed call. Updated `Miner` and `ConvoMiner` to buffer + flush. Modest
   win (embedding was already multi-threaded) but correct.
9. **Fix 3 — SQLite-backed opencode reader.** The file-based
   `~/.local/share/opencode/storage/` has 8 sessions; the real data
   (**2,559 sessions**, 81k messages, 355k parts) lives in `opencode.db`.
   Wrote a new reader at `crates/mempalace-server/src/opencode_reader.rs`
   with both code paths (SQLite primary, file walker fallback) and added
   `--mode opencode` to the CLI.
10. **Ran the three convo mines** against `~/.mempalace`:
    - Claude Code: 43,767 drawers (16:24)
    - Codex: 1,148 drawers (0:47)
    - Opencode: 69,297 drawers from 2,523 sessions (49:47)
    - **Subtotal: 114,212 drawers**
11. **Fix 4 — concurrency model.** Realised that with 4 agents each spawning
    their own `mcp-serve`, they'd race each other on the palace. Added an
    exclusive `fs2` file lock to `LanceDbPalace::new`, built a Unix-socket
    transport `serve_unix_socket` in `mcp_transport.rs`, added a
    `mempalace daemon` subcommand that owns the palace + lock + socket, and
    added `mempalace mcp-serve --connect <sock>` which is a pure byte pump
    from stdin/stdout to the socket. Agents now all proxy through the single
    daemon. Single writer, no races, verified with Claude Code's MCP health
    check.
12. **Ran the tardis project mine** (43 dirs, `--mode projects`, one wing per
    folder). Got through **27 of 43 projects** before performance tanked —
    `mtd` took 30 min alone, `multi` was still running at 25 min with no end
    in sight. Root cause: `add_many` did an `id IN (...)` SELECT on every
    batch, which is O(palace_size) per batch. At 300k drawers this was
    quadratic in wall time.
13. **Fix 5 — BTree scalar index + merge_insert.** Added a BTree index on the
    `id` column in `LanceDbPalace::new_with_table` (idempotent via
    `list_indices()`). Replaced the dedup SELECT with LanceDB's native
    `merge_insert(&["id"]).when_not_matched_insert_all()`. Rebuilt.
14. **Fix 6 — id prefilter** (because fix 5 alone still embedded every row
    regardless of whether it'd survive merge_insert, and embedding is the
    real cost). Re-added the `id IN (...)` SELECT *but now against the BTree
    index* — O(batch_size × log N) — and skipped embedding for rows that
    already exist. Smoke test: re-mining fully-indexed `crazy-taxi` dropped
    from **66 s → 1.37 s (48× faster)**.

## Where we are now

- Palace: `~/.mempalace/` at ~4.2 GB, **327,718 drawers** committed.
- Daemon: **stopped** — we killed it so the mining rebuilds could run.
- Four agents: still configured with `--connect`, but MCP will be unhealthy
  until the daemon is restarted.
- `multi` tardis project: partially mined and then killed mid-stream. Palace
  row count unchanged from before `multi` resume, but LanceDB files grew
  ~500 MB (staged/uncommitted transactions presumably — harmless).
- New binary at `target/release/mempalace` (mtime 2026-04-13 14:31) has
  prefilter + merge_insert + BTree index + file lock + daemon + proxy.
- `CLAUDE.md` in repo root has the full operator's runbook.

4. **Auto-start the daemon on login.** Drop a systemd `--user` unit at

   Template:

   ```ini
   After=default.target
   [Service]

   RestartSec=2
   [Install]
   WantedBy=default.target
   ```
5. **Fix SIGTERM cleanup.** `cmd_daemon` at
   `crates/mempalace-cli/src/main.rs:418` catches `tokio::signal::ctrl_c()`
   but not `SignalKind::terminate()`. Add a second branch to the `select!`
   so SIGTERM also removes `mempalace.sock` + `mempalace.pid`. Five lines.
6. **Add `--connect` to `search` and `status`.** Currently these CLI

### Medium-term improvements

7. **Two-level drawer IDs** so re-mining a project doesn't re-read unchanged
   files at all. Outer hash = `sha256(path + chunk_idx)`, inner hash =
   `sha256(content)`. If outer matches, skip file I/O entirely. Would turn
   project re-mines from seconds into milliseconds. Touches
   `Miner::chunks_into_buffer` and the schema.
8. **Content-change detection.** Instead of (or in addition to) #7, track
   file mtime per source and skip unchanged files at walk time.
9. **Incremental convo mining.** Right now the convo mines re-scan every
   session JSONL each run. Track the highest `time_created` per wing, only
   read sessions newer than that.
10. **Proper daemon CLI.** Add `mempalace daemon-stop` (sends SIGTERM to
    the pid in `mempalace.pid`), `mempalace daemon-status`, and
    `mempalace daemon-restart` wrappers so operators don't need to know
    about the pidfile.
11. **Remove stale `hooks/` directory.** It's the pre-port shell hooks
    that shell out to `python3 -m mempalace`. Only runs if you explicitly
    install the plugin, but it's stale references to the now-deleted
    Python package. Low priority but it's misleading.

### Far-future / if we really care

12. **GPU embedding.** Not worth it yet — AllMiniLML6V2 is small and
    batching + prefilter already give us linear scaling. If mining truly
    becomes a pain, the path is `fastembed = { features =
    ["ort-load-dynamic"] }` + ship CUDA-built `libonnxruntime.so` +
    matching CUDA toolkit + cuDNN. Read: a full evening of yak-shaving.
13. **Gemini session parser.** Four agents configured but only three
    mined. Gemini stores sessions under `~/.gemini/tmp/<hash>/chats/*.json`
    in its own format — no parser in `normalize.rs` yet. The shape is
    known (we peeked during the opencode investigation) so it's maybe
    40 lines in `try_gemini_json()` modeled after `try_codex_jsonl`.
14. **Bulk-insert MCP tool.** Would let the miner route through the
    running daemon instead of requiring a stop/start cycle. Nice UX
    improvement, but non-trivial: needs a new streaming tool that
    accepts `Vec<DrawerRecord>` per call, not one drawer at a time
    like the existing `mempalace_add_drawer`.
15. **Re-embed / re-index tooling.** If we ever change the embedding
    model or the schema, we need a bulk re-embed path. Today the only
    way is `rm -rf ~/.mempalace && cargo mine everything again`.

### Known rough edges (document but don't fix)

- Two plaintext secrets still sitting in `~/.config/opencode/opencode.json`
  (GitHub PAT, z.ai API key). Flagged early in the session. Not mempalace's
  problem, but noting it since we walked past them.
- `.lock.pid` file in `~/.mempalace/` is a courtesy marker, not the actual
  lock. The real lock is the `fs2::lock_exclusive` held on the File handle
  inside `LanceDbPalace`, which releases on drop. Don't treat `.lock.pid`
  as authoritative.
- `MEMPALACE_ALLOW_MODEL_DOWNLOAD` env var is named misleadingly — it only
  gates an `#[ignore]`'d test in `lancedb_backend.rs`, not runtime behavior.
